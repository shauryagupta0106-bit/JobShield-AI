# PART 1: PRODUCT VISION

## 1.1 Project identity

**Product name:** JobShield AI

**Tagline:** Verify Before You Apply.

**Product category:** AI-powered job and internship verification platform.

**Primary audience:**
- College students searching for internships.
- Fresh graduates applying for their first jobs.
- Early-career professionals.
- Job seekers receiving recruitment messages through social media, email, messaging apps, job boards, and unofficial websites.

**Core promise:**

Help people investigate suspicious job opportunities by comparing the claims in a job listing with available evidence, identifying warning signals, and explaining what they should verify before taking action.

JobShield AI must feel like a credible, thoughtfully designed cybersecurity product that an actual startup could launch. It must combine excellent visual design, practical functionality, transparent analysis, and responsible handling of evidence.

## 1.2 The problem

Job seekers may encounter:
- Job advertisements that impersonate real companies.
- Fake recruiters using legitimate company names or branding.
- Requests for registration, interview, training, security deposit, or other upfront payments.
- Suspicious application links and domains.
- Salary, role, location, or eligibility claims that conflict with other sources.
- Misleading job descriptions copied from legitimate vacancies.
- Recruitment messages that pressure people into acting immediately.
- Opportunities that are difficult to verify using manual internet searches.

Users often need to open multiple websites, compare company career pages, inspect recruiter details, and interpret inconsistent information themselves.

## 1.3 Our solution

JobShield AI should let users submit a job opportunity through one interface and receive a structured, evidence-backed investigation report.

The platform should:
1. Accept a job URL, pasted job text, recruiter message, or supported PDF document.
2. Extract the relevant details.
3. Identify potential warning signals using transparent rules.
4. Research relevant public web pages using TinyFish Search and Fetch.
5. Compare the submitted claims with available official and corroborating sources.
6. Use an LLM for structured extraction and clear explanations when configured.
7. Present source links, supporting excerpts, discrepancies, limitations, and recommended next steps.
8. Allow users to report suspicious opportunities through a moderated workflow, where implemented.

The product must never guarantee that a job is genuine or fraudulent.

## 5.2 Rule-based warning signals

Implement explicit, understandable checks, such as:
- Recruitment, registration, interview, or training fee requests.
- Requests for deposits or payment before employment.
- Mismatch between a claimed official domain and the supplied application domain.
- Contradictory company, role, salary, or location details.
- Suspicious urgency or guaranteed-job claims.
- Missing or inconsistent recruiter identity.
- Links that redirect to unexpected domains.
- Job descriptions that substantially differ from the purported official vacancy.

Rules should explain why they fired.

Do not automatically treat high salary, poor grammar, an absent listing, or a small company as proof of fraud.

Use a versioned scoring methodology. If a score is shown, label it a heuristic risk indicator rather than a probability unless independently validated.

Where evidence is insufficient, show an insufficient-evidence or unable-to-verify status.

Use the documented API endpoints, authentication header, request bodies, response formats, error codes, and rate limits.

Requirements:
- Store the API key in a backend environment variable.
- Never expose the key to frontend JavaScript.
- Add connection timeouts.
- Handle HTTP errors and rate limits.
- Parse responses safely.
- Preserve source URLs.
- Store retrieval timestamps.
- Deduplicate relevant sources.
- Avoid unnecessary requests.
- Provide a graceful error state when the service is unavailable.

Use Search to discover relevant public sources and Fetch to retrieve pages where supported.

Prioritize official company domains and career pages. Use other sources as corroborating evidence rather than treating search ranking as proof.

Do not invent API responses or fake successful research.

If credentials are missing, implement the integration properly, add a clear configuration guide, and make the unavailable state explicit. Never silently substitute fabricated results.

- Inferences.

# PART 7: SECURITY AND PRIVACY

Implement and test:

- Reject localhost, loopback, private, link-local, and restricted network destinations.

- Revalidate redirects.

### File safety
- Restrict accepted file types.
- Validate actual content where possible, not just filename extensions.
- Set file-size and processing limits.
- Reject unsupported or malformed documents safely.
- Avoid executing uploaded content.
- Clean up temporary files.

- Add `.env` files to `.gitignore`.
- Provide `.env.example` files with placeholders only.
- Never print secrets into logs.
- Never include real keys in documentation or frontend bundles.

### Prompt injection
- Treat webpage and document content as data, not instructions.

- Validate all model outputs against a schema.
- Never allow retrieved content to trigger arbitrary tools or privileged actions.

### Privacy
- Minimize data collection.
- Explain how uploaded content is used.

- Do not publicly expose private recruiter details.
- Provide deletion or retention behavior appropriate to the implemented features.
